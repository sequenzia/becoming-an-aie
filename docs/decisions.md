Decisions in force for this repository, the items still open, and the deviations that wait for the author's sign-off. The blueprint (`docs/architecture.md`, section 15) is the source; this file is the running record. Anyone may append a dated entry. Newer entries go at the end of each section. ## 1. Decisions in force (2026-09-15, from the blueprint, section 15.1)

1. Two env models, stated once. Public server variables (`SITE_URL`, `FEATURE_ACCOUNTS`, `PREVIEW_DRAFTS`) are build-time constants and Docker build arguments. Everything that must vary per environment at runtime is declared `access: 'secret'` even when it is not sensitive (`BETTER_AUTH_URL`, `EMAIL_PROVIDER`, `PG_CA_FILE`, `PGLITE_DATA_DIR`). The Secret never carries a public variable, and `createPgDb` refuses a plaintext connection in production.
2. Secrets are optional in the astro:env schema and enforced in `src/lib/env.ts`. Builds and content checks need no secrets. `/readyz` reports missing ones in the log only.
3. Lazy `getDb()` and `getAuth()` instead of module-level instances. Nothing connects until the first on-demand request.
4. Phase commits are cut as in blueprint section 1.3. Phase 0 ships the scaffold, the public pages, the notify flow, delivery, and the content skeletons, with B and D as permitted placeholders hidden behind `FEATURE_ACCOUNTS=false`.
5. `PREVIEW_DRAFTS` renders drafts in dev and the CI e2e build, never in an image. The Phase 1 fixture area module (`models.mdx`, still a draft) is how the module layout, forms, island, and prerequisite notice get verified before Phase 2.
6. The content map lives in code (`AREA_CONTENT_MAP`, `ELECTIVE_MODULES`, `ORIENTATION_MAP`, `FOUNDATIONS_MAP`, `TRANSFER_TABLE`, `FORBIDDEN_CHAPTERS`) and is enforced by `moduleRules` and the content check. The CG-20 transfer row assignment: models testing; context decomposition; tools interface; orchestration decomposition; evals testing; operating observability, security, operations.
7. `transferRows`, `<Takeaway />`, `<Outcomes />` give the frontmatter fields a rendering contract.
8. Order is numbered within a kind (area 1 to 6, elective 1 to 5, others 0). The catalog sorts by kind, then order.
9. Hand-written `src/db/auth-schema.ts`, no Better Auth CLI dependency (CG-34). The optional diff uses `scripts/auth-cli.config.ts` and `npx auth@1.7.5`.
10. Stateless HMAC tokens, no `token` column (CG-16). Confirm tokens expire after 30 days; unsubscribe tokens never expire. A confirm token issued before the row's `unsubscribedAt` (or before its `createdAt`) is invalid, and every subscribe mints fresh tokens.
11. Account deletion by Drizzle transaction, not `auth.api.deleteUser` (CG-9). Session cookies are cleared by name with the attributes Better Auth set. One click, no wrapper.
12. `accountLinking.enabled: false` (EC-5.9.1). A second provider with the same email is rejected; the sign-in page explains it.
13. Data minimization through `mapProfileToUser` (returning `image: undefined`) plus database hooks that null the avatar, IP, user agent, provider tokens, and scope. The effect on real rows is a Phase 1 gate check.
14. Better Auth gets a single-value `x-forwarded-for` from `clientAddress` in the catch-all route instead of a `trustedProxies` CIDR.
15. Module pages are readable by anyone (CG-31). Only the forms, self-check persistence, `/account`, `/account/plan.md`, and `/assessment` need sign-in.
16. Orientation stays prerendered and its self-check is local-only for everyone (deviation 3.3 below). Manual completion posts to the on-demand `/progress` route.
17. Catalog renders on demand with cache headers (CG-5): `private, no-store` with a session or on a protected route, `public, max-age=300` otherwise.
18. The closing module is two things: a readable module at `/modules/self-assessment` and a guarded tool at `/assessment`.
19. Failure-exercise reveal is server-side through a named slot rendered only when a `failure` response exists, together with the pitfall band.
20. Self-check mastery rule: per-question "correct once" in the island; the action stores the latest best answers and sets `passed` to true when all are correct or it was already true. Unknown answer keys are dropped and the record is bounded by `SELF_CHECK_MAX`.
21. Plan ranking: score is `2 * gapNew + gapTransfer` with gaps as mean distance from 3. Focus is the top three areas with a gap. Uniform high means every item rated 3. Every focus carries the learner's feature.
22. Plan text is editable Markdown, exported verbatim; the structured plan is regenerated on retake and never edited. Only the latest version is editable.
23. No Preact outside the two islands. Workshop and failure forms are HTML forms with a small enhancement script.
24. One inline theme script in `Base.astro` (CG-6). The toggle buttons carry no script.
25. Diagrams sit on a dark tile in both themes (CG-26). Highlight states use CSS on one inline SVG addressed by `data-layer`; the import script strips every id.
26. Heading ids are computed with a minimal slugger (`src/lib/slug.ts`) that matches github-slugger for ASCII headings. Authors keep headings ASCII.
27. Migrations run as a Job before rollout, `oc exec` fallback, never at container start.
28. CI on GitHub Actions, image on GHCR (CG-27), pending the author's confirmation of the registry. Actions are pinned to commit SHAs at implementation time.
29. The RDS CA bundle is committed in `certs/`, and `scripts/tls-check.mjs` proves TLS from inside the pod.
30. `README.md` skeleton lists the scripts, the layout, the phase commit rule, and links to `docs/`.
31. Feedback is anonymous with no user column (CG-15). It is not removed by account deletion.
32. Rate limits as in blueprint section 7.6: workshop and failure saves 30 per account per hour and 60 per IP per hour (CG-25). Better Auth's own limiter stays on in production for `/api/auth/*`.
33. No committed env file. Vitest placeholders live in `vitest.config.ts`; Playwright placeholders in `e2e/env.ts`. The notify token secret is `NOTIFY_TOKEN_SECRET`.
34. The landing page lists drafts as planned modules so the fourteen names come from content.
35. Elective, foundations, and area modules share the six-to-twelve question rule; orientation needs at least one question; closing has none (CG-24).
36. Foundations is treated as a Phase 2 deliverable (CG-8).
37. ISO dates everywhere (`isoDate`, `<time datetime>`).
38. Response headers: the middleware sets `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, and `X-Frame-Options` on on-demand responses; the Route sets the same four on every response plus HSTS. A Content-Security-Policy is deferred to Phase 4.
39. `/readyz` says only ok or not. Details go to the server log.
40. `scope` is nulled in the account hooks with the tokens, so the privacy notice's list of kept Better Auth fields is exact.
41. Log retention is stated as at most 30 days in the privacy notice and enforced by the runbook; the author confirms the number before the Phase 0 gate.
42. `axe-core` is a direct dev dependency so the island tests run axe under jsdom in each state.
43. The container runs on a read-only root filesystem with privilege escalation disabled and all capabilities dropped.
44. Action tests use the internal `Symbol.for('astro.actionAPIContext')` in exactly one helper.
45. Toolchain (TC-7.6.2): MDX through `@astrojs/mdx` on Astro's default Sätteri pipeline. No `@astrojs/markdown-remark`, no remark or rehype plugins. Preact islands only for the self-check and the self-assessment.

### 2026-09-15, S: the guard redirect carries the private cache headers

Blueprint section 6.4 says the sign-in redirect for a protected route carries `Cache-Control: private, no-store`, and `e2e/landing.spec.ts` (section 12.3) asserts it. The section 6.4 middleware code returns `context.redirect(...)` before `applySecurityHeaders` and `applyPrivateCache` run, so the built server answered the redirect with no cache header (verified with curl against `node dist/server/entry.mjs`). S's Phase 0 placeholder applies both header sets to the redirect response before returning it. B keeps that in the Phase 1 middleware. Observed at the same time: `context.originPathname` for `GET /account` is `/account/` with a trailing slash, because `setOriginPathname` in `astro/dist/core/routing/rewrite.js` appends one whenever `shouldAppendForwardSlash(trailingSlash, buildFormat)` holds, which it does for the defaults (`trailingSlash: 'ignore'`, `build.format: 'directory'`). The redirect is therefore `/sign-in?next=%2Faccount%2F`. `safeNextPath` accepts it. F's spec should compare against the encoded value Astro produces, not a hand-written `%2Faccount`.

- Open item 10 answered by source. `Astro.callAction` from a GET page does not trigger the origin check. In astro 7.3.2, `createCallAction` (`dist/actions/utils.js`) binds the page's context and calls the handler directly. The origin check runs only in `handleAction` (`dist/actions/handler.js`) for an inbound `_action` form POST or an RPC call. `GET /notify/confirm` and `GET /notify/unsubscribe` never reach it. F's e2e spec confirms it at runtime.
- `subscribe` writes `createdAt` from the same `now` it stamps into the tokens, instead of the column default, so the replay rule in `confirm` compares one clock. Without that a test clock in the past would read every fresh token as older than the row.
- `unsubscribe` stamps `unsubscribedAt = now` on every valid call (the 7.5 wording), so the learner's latest unsubscribe outranks every confirm token minted before it. Once a fresh confirm has cleared `unsubscribedAt`, an older confirm token can re-stamp `confirmedAt` but cannot change subscription state. Accepted and pinned by a test. A stricter rule (reject tokens older than the last confirmation) would show "not valid" to a learner who reopens a confirmed link, so it was not adopted.
- `subscribe` accepts an optional `log` in its options (default `console.error`) so the mailer-failure path (EC-5.1.3) is observable in tests without console noise. The failure line names the mailer and the error, never the address. The 7.5 signature is otherwise unchanged.
- `/notify` re-renders the form with the HTTP status of the action error when it is a 4xx (400 for a rejected address, 429 past the limit) and keeps 200 for a 5xx, because Astro swaps in its error page for a 500 status and the message would be lost. `/notify/confirm` and `/notify/unsubscribe` answer 429 with the limiter's message when the `notify-token-ip` rule is exceeded; every other failure renders the one generic message. All three on-demand notify pages send `Cache-Control: private, no-store` through `applyPrivateCache`, so section 14.1's consumer list for that helper gains C.
